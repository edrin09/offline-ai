# 实测数据台账（Benchmarks）

> 全部数据为 2026-10-18 在 Ryzen 7 5800U 实机测得，3 轮取均值。机器有热衰减（±10%），对比看相对值不看绝对值。

## 一、引擎 A/B：ik_llama.cpp vs 官方 llama.cpp（同模型同参数）

| 指标                    | 官方 b11707            | ik_llama build 5481    | 倍数       |
| --------------------- | -------------------- | ---------------------- | -------- |
| 冷 PP（4K token prompt） | 13.9 tok/s（等 4.6 分钟） | **47.9 tok/s**（等 81 秒） | **3.4x** |
| TG @ 4K 上下文           | 5.3 tok/s            | **11.2 tok/s**         | **2.1x** |
| TG 短上下文（500 tok 生成）   | 12.5 tok/s           | **14.5 tok/s**         | +16%     |

结论：全面切换 ik_llama，官方版已弃用（数据留档）。参数语法差异：ik 用 `-ctk/-ctv`，官方用 `--cache-type-k/v`；ik 无 `--swa-full`/`--cache-reuse`（不需要，缓存机制不同）。

## 二、两模型编码速度对比（ik_llama，短上下文）

| 编码任务                 | Coder Q4_K_M | 办公 Q3_K_M |
| -------------------- | ------------ | --------- |
| 开放生成（500 tok）        | 13.9         | **15.3**  |
| 代码改写（350 tok）        | 13.3         | **14.2**  |
| 修 bug + 写测试（400 tok） | **14.4**     | 14.1      |
| TG @ 4K 长上下文         | 11.2         | **13.2**  |
| 冷 PP（4K prompt）      | 47.9         | **61.2**  |

**反直觉结论：办公模型编码比 Coder 还快**（Q3 文件小 2GB，读权重省一截），长上下文下快 18%。日常编码可直接用办公模型；Coder 保留给 tool-calling/Agent 场景。

## 三、上下文衰减曲线（TG，tok/s）

| 上下文       | Coder       | 办公           |
| --------- | ----------- | ------------ |
| 0.5K      | 14.5        | 15.3         |
| 4K        | 11.2        | 13.2         |
| 13~14K（满） | **6.0~6.2** | **6.5~10.1** |

满上下文场景明细：Coder 中等编程 6.11 / 小规模编程 5.99 / 代码改写 6.24；办公 改文件 6.54 / 修 bug 10.12（后者机器凉时测的，偏乐观）。

**上下文是速度杀手**：满上下文速度腰斩。日常保持 < 4K 上下文。

## 四、投机解码实测（桌面文档预期 +30~50%，全部未兑现）

| 方案                | 速度         | 接受率        | 结论             |
| ----------------- | ---------- | ---------- | -------------- |
| ngram-simple      | ≈基线        | 34%        | ❌ 低于 50% 红线，移除 |
| 草稿 0.6B 深度5 p0.75 | 11.3（-10%） | 88%，均长 3.4 | ❌ 开放任务净亏       |
| 草稿 0.6B 深度5 p0.9  | 11.1       | 均长仍 3.4    | ❌ 没救回来         |
| 草稿 0.6B 深度8       | 13.97      | 91%        | ❌ 验证开销反噬       |
| 草稿 0.6B（改写类任务）    | 14.9（+16%） | 均长 4.5+    | ⚠️ 仅改写/模板类回本   |

根因：CPU 上草稿模型 forward 开销（线程同步 + 小 batch）远超理论带宽成本；只有输出大段照抄输入的任务能回本。草稿模型文件保留在 `main/models/Qwen3-0.6B-Q4_0.gguf` 备用。

## 五、缓存机制

- prompt 缓存命中：二次请求 prompt 处理 19s → 73ms（`cache_n=163, prompt_n=1`）
- `--slot-save-path` 存盘：4K 上下文 save 111ms / 205MB；重启 restore 55ms；restore 后同 prompt `prompt_n=1` 全命中（切模型重启后第一轮即热）
- ⚠️ ik_llama 的 prompt 缓存按 **4096 token 分段**复用：13K 上下文每请求重算 ~~9K（PP 20~~31 tok/s），agent 多轮长上下文每轮 prefill 5~6 分钟。**这是当前最大痛点**，缓解靠上下文控制（见 AGENTS.md 纪律第 4 条）

## 六、3×3 速度矩阵：两模型 × 三档上下文 × 三档任务复杂度（2026-10-18 下午复测）

**测法**：

- 上下文填充素材 = **真实记忆层内容**（AGENTS.md + docs 三件 + 一段代码），即"加了记忆功能后"的真实请求形态
- 每格 2 轮：R1 首请求（计量 PP）+ R2 同 prompt 重发（prompt cache 全命中，纯 TG）；TG 取两轮均值
- 统一 `n_predict=300 / temp=0 / top_k=1`，保证两模型、三任务可比
- 满档定 **12K** 而非 15K：15K 会触发内存页回收崩速（见 pitfalls）

### Coder-30B-A3B Q4_K_M

| *上文档位*    | *简单*    | *中等*    | *复杂*    | *档位均值*      | *PP(冷)* |
| --------- | ------- | ------- | ------- | ----------- | ------- |
| *短 ~1.5K* | *14.83* | *14.04* | *12.13* | ***13.67*** | *68.5*  |
| *中 ~8K*   | *8.16*  | *7.26*  | *7.11*  | ***7.51***  | *25.8*  |
| *满 ~12K*  | *6.93*  | *6.45*  | *7.09*  | ***6.83***  | *26.1*  |
| *任务均值*    | *9.97*  | *9.25*  | *8.78*  | *—*         | *—*     |

### 办公-35B-A3B Q3_K_M

| 上文档位    | 简单    | 中等    | 复杂    | 档位均值      | PP(冷) |
| ------- | ----- | ----- | ----- | --------- | ----- |
| 短 ~1.5K | 14.71 | 14.36 | 14.38 | **14.48** | 67.7  |
| 中 ~8K   | 12.21 | 13.12 | 13.29 | **12.87** | 49.9  |
| 满 ~12K  | 12.50 | 12.37 | 12.47 | **12.45** | 41.0  |
| 任务均值    | 13.14 | 13.28 | 13.38 | —         | —     |

### 结论

1. **长上下文办公模型碾压 Coder**：8K 档 +71%（12.87 vs 7.51）、12K 档 **+82%**（12.45 vs 6.83）
2. **衰减曲线完全不同**：Coder 13.67 → 7.51 → 6.83（**-50%**）；办公 14.48 → 12.87 → 12.45（**-14%**，几乎平坦）
3. **任务复杂度对 TG 几乎无影响**：办公三档 13.14/13.28/13.38（复杂反而略高，属噪声）；Coder 短档 14.83→12.13 的下降是**连续负载热衰减**，不是"复杂任务更慢"——结论：不需要为复杂任务单独担心速度，慢的永远是上下文长度
4. **PP 同样办公占优**：8K 49.9 vs 25.8（1.9x）、12K 41.0 vs 26.1（1.6x）
5. **12K 冷 prefill 耗时**：Coder 503.6s（**8.4 分钟**，实测 12034 tok 全量）；办公 5904 tok 用 168s（35.1 tok/s）→ 折算全量 12K 约 **5.7 分钟**
6. Coder 有热衰减（短档第 3 个任务从 14.6 掉到 11.9），办公几乎无衰减（14.7 → 14.5 → 14.4）

## 七、元数据与模型背景

- 两模型 GGUF 均声明 262144 上下文，但**办公模型（empero 蒸馏版）实际按 8K 样本训练**，且 tokenizer 效率约为 Coder 一半（同文本 27K vs 12.9K token，超 16K 直接报错——"回答偏短"的根因）
- 有效带宽估算：14.5 tok/s × 1.9GB/token（3B 激活 Q4）≈ 27GB/s，已达 DDR4-3200 双通道理论峰值的 53%

## 八、编程能力对比：Coder vs 办公（2026-10-18 下午实测）

**测法**：

- 6 道**可自动判分**的编程题，temp=0、pass@1、每题独立会话，Python 单测判定，不靠主观打分
- 题面：电话号归一化 / LRU 缓存 / 拓扑排序 / 日志行解析 / 递归下降表达式求值 / 修 bug（三点均含边界要求）
- 另测 tool-calling 两轮闭环：发 tools → 收 tool_calls → 回填 role=tool → 看能否正确复述结果

| 题目        | Coder   | 办公      | Coder tok | 办公 tok   | Coder 秒  | 办公 秒     | 办公思考字符 |
| --------- | ------- | ------- | --------- | -------- | -------- | -------- | ------ |
| T1 电话归一化  | PASS    | PASS    | 124       | 120      | 7.8      | 9.3      | 17     |
| T2 LRU 缓存 | PASS    | PASS    | 149       | 172      | 10.1     | 13.3     | 17     |
| T3 拓扑排序   | PASS    | PASS    | 241       | 600      | 20.8     | 45.1     | 1441   |
| T4 日志解析   | PASS    | PASS    | 149       | 967      | 12.5     | 70.6     | 2557   |
| T5 表达式求值  | PASS    | PASS    | 521       | 1104     | 47.8     | 81.2     | 1238   |
| T6 修 bug  | FAIL    | FAIL    | 79        | 100      | 6.8      | 7.6      | 17     |
| **合计**    | **5/6** | **5/6** | **1263**  | **3063** | **106s** | **227s** | —      |

### 结论

1. **正确率打平：5/6 vs 5/6**，而且唯一失败点完全相同——T6 两者都用 `intervals.sort()` 原地改了入参，违反"不修改入参"。说明这是两模型共有的边界盲区，不是某个模型的短板
2. **代价差一倍多**：token 消耗办公是 Coder 的 **2.43x**，出结果耗时 **2.15x**（同机连续实测）
3. **根因是"思考税"**：办公模型是 reasoning 模型——简单题几乎不思考（`<think>` 仅 17 字符），一旦遇到中等/难题就进入长思考（1238~2557 字符），token 全烧在思考上；Coder 是 non-thinking，零思考直出代码
4. **tool-calling 两模型都完全正确**：都返回 `get_weather(city=北京, unit=celsius)`，回填 18°C 后都能正常复述。前提是启动必须带 `--jinja`（否则 500，见 pitfalls）
5. **换算到长上下文**（用第六节 TG 折算，推算值）：8K 上下文办公慢约 1.34x、12K 慢约 1.26x——办公的速度优势能抵消一部分 token 劣势，但没有反超

### 选型建议

| 场景                   | 用哪个       | 理由                         |
| -------------------- | --------- | -------------------------- |
| 写/改代码、补全、Agent 工具调用  | **Coder** | 正确率相同，快 2.15x、省 2.4x token |
| 读长文档、问答、总结、会议纪要      | **办公**    | 长上下文快 71~82%，且不产生思考税       |
| 12K 上下文的代码理解（不产出长代码） | 办公可接受     | 折算劣势缩到 1.26x               |
